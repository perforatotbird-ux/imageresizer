# batchresize — GPU-пакетный ресайзер фотографий для Windows

Прототип пакетного конвейера: рекурсивно читает папку с фотографиями, декодирует
JPEG **на GPU** через nvImageCodec/nvJPEG, меняет размер CUDA-ядром и кодирует
обратно в JPEG тоже на GPU. CPU-путь (libjpeg-turbo + SIMD-ресайз из OpenCV)
оставлен как честный baseline и как fallback.

Проверено на: Windows 10 22H2, GeForce GTX 1060 6 GB (SM 6.1, Pascal),
драйвер 581.57, Python 3.13, CUDA 12.9 (pip-пакеты).

```
GPU: 57 файлов/с   CPU: 28 файлов/с   (100 фото 9–24 МП, 1024×1024, q=80)
```

Подробные замеры и разбор узких мест — в [REPORT.md](REPORT.md).

---

## 1. Установка

```bat
install.bat
```

Скрипт создаст `.venv`, поставит зависимости и запустит диагностику.
Вручную:

```bat
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m batchresize --doctor
```

`--doctor` печатает ОС, CPU, RAM, GPU, версию драйвера (через NVML), объём VRAM,
версии пакетов и результат сквозного self-test GPU-пути (decode → resize →
encode). Если GPU-путь не работает — вы увидите это сразу, а не в середине
обработки.

**Только CPU (без NVIDIA):**

```bat
.venv\Scripts\python.exe -m pip install numpy pillow opencv-python-headless piexif pytest
.venv\Scripts\python.exe -m batchresize -i D:\Photos -o D:\Out --backend cpu
```

## 2. Быстрый старт

Папки фиксированы: положите фотографии в `input\`, результат появится в
`output\` с сохранением структуры подпапок. Двойной клик по `run.bat` открывает
меню с пресетами, а пункт **9** запускает графический интерфейс.

```bat
rem меню: пресеты, потоки, бенчмарк, диагностика, UI
run.bat

rem всё из .\input в .\output, 1024 px, качество 80
run.bat --size web_1024 --quality balanced

rem превью 256 px, обрезка по центру
run.bat --size thumb_256 --mode cover --quality compact

rem произвольный размер и качество
run.bat --size custom --width 800 --height 600 --jpeg-quality 88

rem масштаб в процентах / мегапикселях / по длинной стороне
run.bat --sizing percent --sizing-value 50
run.bat --sizing megapixels --sizing-value 2
run.bat --sizing longest --sizing-value 1920

rem тест на 20 файлах, без изменения исходников
run.bat --limit 20

rem сравнение GPU и CPU на одном наборе
run.bat --benchmark --limit 100

rem графический интерфейс со всеми настройками
run.bat --gui
```

`-i/--input` и `-o/--output` остались как необязательное переопределение
(удобно для тестов и скриптов); по умолчанию всегда `input\` → `output\`.

После каждого запуска в выходной папке появляется `report.json` (или путь из
`--report`): сколько файлов, сколько ошибок, байты до/после, среднее время по
стадиям.

### Пресеты размера

| Пресет | Рамка |
|---|---|
| `thumb_256` | 256 × 256 |
| `small_512` | 512 × 512 |
| `web_1024` | 1024 × 1024 |
| `large_1600` | 1600 × 1600 |
| `custom` | `--width` × `--height` |

`contain` — вписать целиком, пропорции сохраняются, обрезки нет.
`cover` — заполнить рамку, пропорции сохраняются, лишнее обрезается по центру
(результат ровно `width × height`).

Мелкие фотографии **не увеличиваются** по умолчанию: фото 120×90 при
`--size web_1024` останется 120×90. Нужно увеличение — `--allow-upscale`.
`cover` — исключение: он по определению заполняет рамку, поэтому увеличивает.

### Пресеты качества JPEG

| Пресет | q | Комментарий |
|---|---|---|
| `maximum` | 95 | визуально без потерь, крупные файлы |
| `high` | 90 | высокое качество, крупные файлы |
| `balanced` | 80 | разумный компромисс (по умолчанию) |
| `small` | 60 | экономия места, потери заметны |
| `light` | 90 | почти без видимых потерь |
| `medium` | 80 | рекомендуется |
| `strong` | 65 | заметно меньше размер |
| `extreme` | 50 | максимальное сжатие |

Старые имена `compact` (65) и `very_high` (95) продолжают работать.

### Методы масштабирования (`--sizing`)

| Метод | Что делает | `--sizing-value` |
|---|---|---|
| `resolution` | вписать в рамку `--width` × `--height` | не используется |
| `percent` | уменьшить до N % от исходника | `50` = половина |
| `megapixels` | уменьшить до N мегапикселей | `2` = 2 МП |
| `longest` | длинная сторона = N px | `1920` |
| `shortest` | короткая сторона = N px | `1080` |

`--sizing` работает вместе с `--mode` (`contain`/`cover`): метод задаёт целевой
бокс, режим решает, как в него вписываться.

Значение реально передаётся кодировщику (`nvjpegEncodeImage` на GPU,
`cv2.imencode` на CPU) — это проверяется тестом на монотонность размера файла.

### Цветовая субдискретизация

`--subsampling auto` повторяет логику mozjpeg:

* q ≤ 85 → **4:2:0** (2×2 усреднение цветности): файл меньше всего, но мелкие
  цветные детали и резкие цветные границы «плывут»;
* q 86–94 → **4:2:2** (усреднение по горизонтали);
* q ≥ 95 → **4:4:4** (без усреднения): цветные детали без потерь, файл крупнее
  на 10–25 %.

Яркость (Y) не усредняется никогда — глаз чувствителен именно к ней, поэтому
визуальная разница между 4:2:0 и 4:4:4 на фотографиях невелика, а по размеру
она заметна.

## 4. Как устроен конвейер

```
обнаружение файлов (os.scandir, рекурсивно, без выходной папки)
        │
        ├─ N потоков чтения ──► [очередь задач, ограниченная] ──► GPU-поток
        │        (read + разбор заголовка + EXIF + расчёт геометрии)     │
        │                                                               ▼
        │                                        пакетное декодирование nvJPEG
        │                                        (batch_size изображений за вызов)
        │                                                               │
        │                                        box-префильтр (если downscale > 4×)
        │                                                               │
        │                                        CUDA-ресэмплинг (2 прохода)
        │                                                               │
        │                                        nvJPEG encode (q + chroma)
        │                                                               │
        └─ M потоков записи ◄── [очередь результатов, ограниченная] ◄───┘
                 (temp-файл + os.replace)
```

Ключевые решения:

* **Один CUDA-контекст на процесс, один GPU-поток.** Контекст создаётся один раз
  при старте; никаких `cudaSetDevice`/инициализаций на файл.
* **Пакетное декодирование.** `Decoder.decode([CodeStream, ...])` — один вызов
  nvJPEG на весь пакет, а не N вызовов с накладными расходами.
* **Ограниченные очереди.** Между стадиями стоят `queue.Queue(maxsize=N)`:
  быстрый диск не заваливает память, а медленный GPU притормаживает чтение.
* **Никаких копий RAM↔VRAM в горячем пути.** nvImageCodec декодирует сразу в
  device-буфер (`STRIDED_DEVICE`), CuPy оборачивает его через
  `__cuda_array_interface__` без копирования, ядра пишут результат в VRAM,
  nvJPEG кодирует прямо из VRAM. Через PCIe едет только сжатый битстрим
  (~10–50 КБ на файл).
* **Бюджет VRAM.** Размер пакета ограничивается не только `--batch-size`, но и
  `--vram-budget`: суммарное число пикселей в полёте умножается на 4 байта и
  сравнивается с бюджетом. Пакет из 8 файлов по 24 МП не выест 6 ГБ.
* **Разделяемые таблицы весов.** Таблица ресемплинга зависит только от
  (src_len, dst_len, scale, offset, filter) и кешируется на GPU: тысячи фото
  одного размера переиспользуют одни и те же таблицы.

### Почему не `cv2.resize` и не Pillow

В GPU-пути не используются ни Pillow, ни `cv2.imread/imresize/imwrite`.
Ресайз — два CUDA-ядра (`rs_h`, `rs_v`) с предвычисленными весами
(Lanczos3/Triangle/Box) и антиалиасингом: при уменьшении ядро растягивается
пропорционально коэффициенту, поэтому 24 МП → 256 px не даёт муара.

При сильном уменьшении (более 4×) сначала выполняется целочисленное
box-уменьшение (`box_reduce`, коалесцированные чтения), а затем Lanczos3 по
уменьшенной картинке — это та же идея, что `PIL.Image.reduce()`, и она
сократила время ресайза 24 МП → 1024 px с 17.6 мс до 3.6 мс, одновременно
улучшив PSNR относительно эталона PIL (50.9 → 52.0 дБ).

### Ориентация EXIF

nvImageCodec сам применяет EXIF Orientation при декодировании (проверено на
всех 8 значениях против `PIL.ImageOps.exif_transpose` — расхождение в пределах
шума JPEG), поэтому в GPU-пути дополнительного прохода нет. CPU/hybrid-пути
применяют поворот вручную (`cv2.rotate`/`flip`, CuPy-срезы).

В выходном EXIF тег Orientation принудительно ставится в 1 — иначе просмотрщики
повернули бы уже повёрнутое изображение второй раз.

### Метаданные

* EXIF копируется (кроме превью, привязанного к старой ориентации).
* ICC-профиль копируется, большие профили (>64 КБ) корректно режутся на
  несколько APP2-сегментов по спецификации ICC.
* Отключается через `--no-exif` / `--no-icc`.

### Прозрачность

PNG с альфа-каналом (определяется по IHDR, а не по расширению) декодируется в
RGBA и сплющивается на CUDA-ядре `alpha_over` с фоном `--bg-color`. WebP/TIFF с
альфой обрабатываются тем же путём, если декодер отдаёт 4 канала, иначе
альфа-канал отбрасывается.

### Надёжность

* **Атомарная запись**: данные пишутся в `.<name>.<pid>.<tid>.tmp` в той же
  папке, затем `os.replace`. Прерванный запуск не оставляет полуфайлов.
* **Ctrl+C**: обработчик ставит `stop`, читатели останавливаются, текущий пакет
  дорабатывается, очередь результатов дописывается на диск, отчёт печатается.
* **Повреждённые файлы**: нечитаемый заголовок, мусор, обрезанный JPEG (без
  маркера EOI) — файл пропускается с записью в `errors`, остальные
  обрабатываются. `--allow-truncated` заставляет декодировать обрезанные.
* **Ошибки доступа/OOM**: файл попадает в ошибки, конвейер продолжается;
  при OOM пакет дробится и повторяется.
* **Коллизии имён**: `photo.png` и `photo.jpg` в одной папке дадут `photo.jpg`
  и `photo__2.jpg` — молчаливой перезаписи нет.
* **Выходная папка внутри входной** исключается из сканирования, повторного
  захвата собственных результатов не происходит.

## 5. Бэкенды

| Бэкенд | Декод | Ресайз | Кодирование | Когда |
|---|---|---|---|---|
| `gpu` | nvJPEG (VRAM) | CUDA | nvJPEG (VRAM) | есть NVIDIA GPU |
| `hybrid` | CPU (Pillow) → VRAM | CUDA | nvJPEG | экзотические форматы, отладка |
| `cpu` | libjpeg-turbo (OpenCV) | OpenCV SIMD | libjpeg-turbo | нет GPU / baseline |
| `auto` | — | — | — | `gpu`, если доступен, иначе `cpu` |

* `--backend gpu` **не** переключается на CPU молча: если GPU-стек не поднялся
  или не прошёл self-test, программа завершается с кодом 2 и внятным сообщением.
* `--backend auto` всегда печатает, какой путь реально использовался
  (`engine : gpu` / `engine : cpu`), и указывает его в отчёте.
* Если отдельный файл не декодируется GPU-бэкендом, он обрабатывается
  fallback-путём (CPU-декод → GPU-ресайз → GPU-кодирование) и учитывается
  отдельным счётчиком `fallback_files` в отчёте. `--no-fallback` отключает это.

## 8. Известные ограничения

1. **Декодирование — узкое место** (~12 мс на 16 МП на GTX 1060). У Pascal нет
   аппаратного JPEG-декодера nvJPEG (он появился в Turing), поэтому работает
   программный GPU-путь. Ограничение упирается в декодер, а не в ресайз.
2. **Ускорение ~2×, а не 5–10×.** CPU-baseline здесь не наивный: libjpeg-turbo
   плюс SIMD-ресайз OpenCV на 8 потоках. На GPU выигрыш даёт декодер, но
   масштабируется он не идеально.
3. **Нет прогрессивного JPEG-декодирования на GPU** (progressive JPEG
   декодируется, но медленнее baseline).
4. **Lossless JPEG (SOF3) не поддерживается** на SM 6.1: nvJPEG возвращает
   `arch mismatch`, файл уходит в fallback.
5. **16-битные PNG/TIFF** приводятся к 8 битам (для JPEG это неизбежно).
6. **Многокадровые TIFF**: обрабатывается первый кадр.
7. **Один GPU**; выбор устройства не реализован (`device 0`).
8. **`--benchmark` измеряет и кэш ОС**: первый прогон может быть медленнее
   (чтение с диска), последующие — быстрее (страничный кэш). В отчёте берётся
   лучшее время из `--benchmark-repeats`; для честного «холодного» замера
   ориентируйтесь на первый прогон.
9. **Прогресс-строка** пишется в stdout через `\r`; при перенаправлении вывода
   в файл она выглядит как одна длинная строка.
10. **Первый прогон по «холодному» кэшу упирается в диск.** На медленном томе
    чтение 40 МиБ заняло ~2.5 с и общая скорость упала до 7 файл/с, тогда как
    повторный прогон тех же файлов дал 31 файл/с. Смотрите стадию `read` в
    `report.json`: если она доминирует — узкое место не GPU.
11. **UI требует tkinter.** Окно рисуется интерпретатором с tkinter, а сама
    обработка идёт в `.venv` (там GPU-стек). Если у `.venv` нет tkinter,
    `--gui` автоматически перезапускает окно через подходящий Python из
    `LOCALAPPDATA\Programs\Python` или из `PATH`.

## 9. Графический интерфейс

```bat
run.bat            rem меню, пункт 9
run.bat --gui      rem сразу окно
```

Четыре вкладки повторяют порядок работы:

| Вкладка | Что настраивается |
|---|---|
| **Input** | исходная и выходная папки, лимит файлов, подсчёт количества |
| **Modify** | метод масштабирования (resolution/percent/MP/стороны), пресет размера, W×H, contain/cover, увеличение мелких, фильтр |
| **Output** | пресет качества (8 вариантов), слайдер q, chroma 4:4:4/4:2:2/4:2:0/auto, фон прозрачности, EXIF/ICC, skip/overwrite |
| **Advanced** | backend, потоки, GPU-батч, глубина очередей, VRAM-бюджет, CPU-fallback, truncated, Huffman, fsync |

Внизу — прогресс-бар, текущая скорость, счётчики потоков и живой лог
(строки вида `42/100 files | 12.3 file/s | 3.4s | threads: ...`). Кнопка
**Cancel** завершает дочерний процесс; уже готовые файлы остаются.
**Environment check** печатает тот же отчёт, что `--doctor`.

Интерфейс запускает обработку отдельным процессом, поэтому окно не
замерзает и GPU-конвейер работает на полную скорость. Отчёт по-прежнему
пишется в `output\report.json`.

## 10. Если что-то не работает

| Симптом | Что делать |
|---|---|
| `FATAL: GPU backend requested but unavailable` | `run.bat --doctor`; проверить драйвер, `nvidia-smi`, что установлены `cupy-cuda12x` и `nvidia-nvimgcodec-cu12` |
| `Failed to find CUDA headers` | поставить `nvidia-cuda-runtime-cu12 nvidia-cuda-nvcc-cu12 nvidia-cuda-nvrtc-cu12` или задать `CUDA_PATH` на установленный CUDA Toolkit |
| `[nvjpeg_lossless_decoder] arch mismatch` | безобидное предупреждение: lossless JPEG не поддержан на этой архитектуре, файл пойдёт через fallback |
| `cudaErrorMemoryAllocation` | уменьшить `--batch-size` и/или `--vram-budget` |
| Медленно на сетевом диске | увеличить `--workers` (латентность мелких записей скрывается потоками) |
| `nvjpeg2k/nvTIFF` ошибки при старте | безобидно: не установлены опциональные расширения JPEG2000/TIFF |
| Окно UI не открывается | нужен Python с tkinter; `--gui` сам ищет его в `LOCALAPPDATA\Programs\Python` и `PATH`, иначе поставьте python.org-сборку |
